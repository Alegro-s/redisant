# Эксплуатация NEXUS: риски и чеклист

Материал для **DevOps** и ответственных за прод: что может «внезапно сломаться» после выкладки и какие инварианты нужно соблюдать. Детали развёртывания — в [DEPLOY.md](../DEPLOY.md); границы продукта — в [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md).

---

## 1. CORS, cookie и HTTPS

**Симптомы:** вход в веб-консоль «сбрасывается», 401 на каждом запросе, сессия не создаётся.

**Причины:**

| Проблема | Что происходит |
|----------|----------------|
| Origin админки не в `CORS_ALLOWED_ORIGINS` | Браузер блокирует ответы или не передаёт credentials. |
| CORS без поддержки credentials | Cookie `nexus_session` не участвует в кросс-доменных запросах. |
| HTTP в браузере + `Secure` на cookie | Cookie не сохраняется или не отправляется. |
| API и фронт на разных доменных зонах без явной настройки | Те же эффекты; нужен точный список origin со схемой и портом. |

**Действия:**

1. В `CORS_ALLOWED_ORIGINS` перечислите **все** реальные origin клиентов: `https://admin.example.com`, локально `http://127.0.0.1:3000` (см. `admin-panel/vite.config.ts`) и т.д.
2. Выдавайте консоль и API за **HTTPS** в проде; проверьте флаги cookie на сервере (`SESSION_COOKIE_SECURE`, окружение `production`).
3. Убедитесь, что фронтенд запрашивает API с **`withCredentials`** (в этом репозитории так и сделано для админки).

Подробнее про консоль: [WAYPOINT_METRICS.md](WAYPOINT_METRICS.md).

## 2. Миграции и версия `server`

**Симптомы:** паники при старте, ошибки SQL, отсутствующие таблицы.

API применяет миграции **при старте** бинарника. Несовпадение версий приводит к хаосу:

- **Старый бинарник + новая БД** — ожидаются старые схемы, возможны ошибки.
- **Новый бинарник + старая БД** — не хватает таблиц/колонок (очереди VK, Waypoint и т.д.).

**Действия:** выкатывать **одну версию** артефакта `server` вместе с **тем набором миграций**, который к ней относится (один коммит / один релиз-тег). После деплоя — `GET /ready` и смоук на критичных эндпоинтах.

## 3. RBAC: `admin`, `nexus` и разрозненные проверки

**Симптомы:** часть экранов открыта, часть API отвечает 403; ожидание «всё вижу» не совпадает с реальностью.

**Контекст:** часть обработчиков использует централизованный `authz` (`require_staff` / `require_nexus`), часть исторически опирается на проверки уровня «админ» в коде. Роль **`nexus`** нужна для наиболее чувствительных операций (версии движка, ключи и т.п.).

**Действия:**

1. Проверять **фактическую роль** пользователя в БД.
2. Для новых эндпоинтов — по возможности единый слой проверок, как в `server/src/authz.rs`.
3. Прояснить для команды продукт: кто в бизнес-смысле «admin консоли», кто «nexus» — иначе RBAC будет «ломаться» под ожидания.

Матрица прав в UI: `admin-panel/src/app/authz.ts`.

## 4. `/me/db/query` и сырой SQL в админке

**Риск:** при включённых флагах (`ADMIN_ALLOW_RAW_SQL` и связанные) инструменты дают **мощный read-only** (или шире, если включена запись) доступ к данным. Это не только технический, но и **продуктовый/юридический** риск для любых залогиненных лиц с доступом к эндпоинту.

**Действия:** в проде по умолчанию держите опасные флаги выключенными; ограничивайте круг пользователей с ролью `admin`/`nexus`; документируйте политику для клиентов.

## 5. Биллинг (Stripe)

Без реального **`STRIPE_SECRET_KEY`** и настроенных продуктов/checkout логика биллинга остаётся в **демо-режиме**. Для коммерции «из коробки» это не готово — см. [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md).

---

## 6. WebSocket и горизонтальное масштабирование

Realtime-слой держит состояние в процессе API. **Горизонтальное масштабирование** без доработки (sticky sessions, общий бэкенд для комнат, и т.д.) **нетривиально**. Планируйте нагрузку и количество инстансов заранее.

---

## 7. Отсутствие полноценного CI

В репозитории может не быть единого пайплайна на каждый PR. **Регрессии** (миграции, авторизация, ingest) легко пропустить.

**Рекомендуемый минимум для команды:**

- `cargo test`, `cargo clippy` для `server/`;
- сборка `admin-panel` (`npm run build`);
- по возможности `flutter analyze` / тесты на критичных путях `client/`.

---

## 8. Технический долг сервера

Крупный **`main.rs`** усложняет ревью и безопасные изменения. При доработках предпочитайте вынос модулей и точечные тесты; крупные рефакторинги — отдельными задачами.

## Чеклист перед публичным продом

- [ ] `JWT_SECRET` надёжный (≥32 символов), секреты не в git.
- [ ] `CORS_ALLOWED_ORIGINS` содержит точные прод-origin консоли и клиентов.
- [ ] HTTPS на консоли и API; cookie-сессия совместима с `Secure`.
- [ ] `ADMIN_OPEN_REGISTRATION` отключён, если нельзя пускать всех в админ-регистрацию.
- [ ] Версия образа/бинарника `server` соответствует миграциям в репозитории.
- [ ] Проверены `GET /health` и `GET /ready`.
- [ ] Политика по сырому SQL и `/me/db/query` согласована.
- [ ] (При монетизации) Stripe и webhooks в бою, не демо.
