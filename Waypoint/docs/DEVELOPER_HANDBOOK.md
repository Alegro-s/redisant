# Справочник разработчика платформы

Материал для команды, ведущей репозиторий **NEXUS**: пользовательские сценарии, прозрачность по рискам и ссылки на детальную документацию. Публичный продуктовый лендинг консоли намеренно не дублирует технические детали — они собраны здесь и в связанных файлах.

---

## 1. Сценарий пользователя веб-консоли

Типовая воронка **Waypoint Metrics** (метрика / админ-панель):

| Этап | Что происходит |
|------|----------------|
| **Главная** | Описание ценности, шаги, тарифы, модули. |
| **Тариф** | Пользователь выбирает **Basic** или **Pro** (ссылки с `?plan=basic` / `?plan=pro`). |
| **Регистрация или вход** | Создание аккаунта или авторизация; план из query при необходимости сохраняется для онбординга (`sessionStorage`, см. `admin-panel/src/utils/preferredPlan.ts`). |
| **Онбординг** | Первый заход после логина: выбор режима **аренды облака** или **своего сервера** (контекст кабинета; реализация экрана — в приложении). |
| **Кабинет** | Дашборд, метрики, проекты и модули согласно тарифу и **роли** в БД (`user` / `admin` / `nexus`). |

Несоответствие ожиданий («я админ, но раздел недоступен») почти всегда сводится к **фактической роли** и политике API — см. раздел 3 и [WAYPOINT_METRICS.md](WAYPOINT_METRICS.md).

## 2. Прозрачная работа (продакшен и продукт)

Краткий перечень того, что должно быть очевидно команде и заказчику интеграции, чтобы выкладка не «ломалась неожиданно». Подробные чеклисты: [OPERATIONS.md](OPERATIONS.md), [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md).

### 2.1. CORS и cookie-сессия

- Веб-консоль ходит в API с **credentials**; в `CORS_ALLOWED_ORIGINS` должны быть перечислены **точные** origin (схема, хост, порт).
- **HTTP без TLS** при флаге **Secure** у cookie → сессия в браузере может не установиться или не отправляться.
- См. также: [DEPLOY.md](../DEPLOY.md), [WAYPOINT_METRICS.md](WAYPOINT_METRICS.md).

### 2.2. Миграции PostgreSQL

- Миграции применяются **при старте** сервера. Версия **бинарника `server`** и набора файлов `server/migrations` должна быть согласована с окружением.
- Смешение «старый код / новая БД» или наоборот даёт рантайм-ошибки.

### 2.3. RBAC: `admin` и `nexus`

- Часть эндпоинтов завязана на **`require_staff`**, часть на **`require_nexus`**, отдельные проверки могут быть исторически разнесены по `main.rs`.
- Роль **`nexus`** — платформенные операции (например ключи активации, версии движка); ожидание «любой admin видит всё» может не совпасть с API.

### 2.4. `/me/db/query` и сырой SQL в админке

- При включённых флагах — **широкий доступ к данным** для подходящих пользователей (часто read-only, но объём «как у БД»). Это продуктовый и юридический риск; политика должна быть явной.

### 2.5. Биллинг

- Без реальной интеграции **Stripe** в окружении API checkout остаётся в **демо-режиме** — для коммерции «из коробки» недостаточно. См. [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md).

### 2.6. WebSocket и масштаб

- Горизонтальное масштабирование нескольких инстансов API **без доработки** realtime-слоя нетривиально.

### 2.7. Качество и техдолг

- В репозитории может не быть полного **CI**; регрессии ловятся вручную.
- Крупный **`main.rs`** на сервере усложняет сопровождение. У клиента и движка — отдельный список ограничений в [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md).

## 4. Обновление справочника

При изменении пользовательского потока (онбординг, тарифы) или контракта API правьте этот файл и при необходимости [WAYPOINT_METRICS.md](WAYPOINT_METRICS.md) в одном изменении, чтобы лендинг и репозиторий не расходились по смыслу.
